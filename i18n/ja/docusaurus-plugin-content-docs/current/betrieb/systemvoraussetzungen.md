# システム要件と構成

Klacksは、お客様自身のサーバー上でDockerスタックとして動作します。このページでは、どのサービスが起動するか、ホストをどう見積もるかを、推奨値の根拠となる実測値とともに説明します。

## 構成: 5つのサービス

オンプレミスパッケージは、運用に必要なものだけを起動します:

| サービス | イメージ | 役割 |
|---|---|---|
| `klacks-postgres` | `pgvector/pgvector:pg17` | データベース。ベクトル拡張は最初から含まれています |
| `klacks-api` | `ghcr.io/heribertg/klacks-api` | バックエンド。起動時にデータベースのマイグレーションと初期データ投入を行います |
| `klacks-ui` | `ghcr.io/heribertg/klacks-ui` | Angularの画面。nginx経由で配信されます |
| `klacks-updater` | `ghcr.io/heribertg/klacks-updater` | 署名付きアップデートを適用します(apiとuiをまとめて) |
| `klacks-proxy` | `nginx:alpine` | TLS終端とリバースプロキシ |

開発元の社内サービス(開発用ナレッジストア、マーケティング、マーケットプレイス、pgAdmin、certbot、Blazor画面)は、意図的に含まれて**いません**。運営者としてご覧になるのは、ご自身のスタックだけです。

## ホストに必要なもの

- 最低限として**RAM 8 GB、4 vCPU**(下記の計算を参照)。
- Docker Desktop(Windows/macOS)、またはCompose v2対応のDocker Engine(Linux)。**amd64またはarm64**。
- 空きポート**80と443** — `HTTP_PORT`と`HTTPS_PORT`で変更できます。
- `ghcr.io`(イメージ)と`github.com`(署名付きアップデートマニフェスト)への**外向きの**HTTPSアクセス。
- 任意: マーケットプレイスの国別パッケージと言語プラグインのための`klacks-software.ch:7553`へのアクセス。

## メモリ: なぜ8 GBなのか、小さなホストではどうなるか

Klacksは2つの検索モデル(エンベッダーとリランカー)を`klacks-api`プロセスの**内部でローカルに**動かします。どちらのONNXセッションも常時メモリ上に保持され、質問のたびにアンロードされることはありません。

開発元の本番ホストで2026年9月12日に計測した値:

- プロセスのベース負荷: 約1'017 MB
- エンベッダー: 約1'171 MB
- リランカー: 約116 MB
- 合計: 約**2'304 MB**で頭打ち
- 上限2'560 MBの設定では、カーネルが2'471 MBでコンテナを終了させました(OOM)。

そのため、同梱のComposeでは`klacks-api`に**3'584M**と3.0 CPUを設定し、アイドル時のアンロードは無効にしています。スタック全体の計算: 3'584M(api)+ 2'048M(postgres)+ 3 × 256M(ui、updater、proxy)= **6'400 MiB**。8 GBの残りはオペレーティングシステムとファイルキャッシュのために残ります。

**小さなホスト、`klacks-api`に約3 GBの場合:** `.env`に次の**両方の**行を設定してください — メモリの行だけを設定してはいけません:

```bash
KLACKS_API_MEMORY_LIMIT=2560M
KLACKS_API_IDLE_UNLOAD_MINUTES=30
```

アイドル時のアンロードは、30分間アクセスがなかったセッションを解放します。代償として、その後の最初の質問でセッションを再読み込みします(エンベッダーで約2.2〜2.9秒、リランカーで約1.1秒)。1〜5の値は5に引き上げられ、`0`は「アンロードしない」を意味します。

## CPU: コアが少なくても遅くなるだけで、壊れはしません

検索はコアが少なくても動作しますが、遅くなります — 計算量が最も多いのはリランカーの段階です。計測値: 25件の候補で、3.0 CPUでは2'994〜3'163 ms、1.5 CPUでは4'339〜4'860 msで、後者ではさらにサービスが7.15秒スロットリングされました。小さめのホストでは:

```bash
KLACKS_API_CPU_LIMIT=1.5
```

スタックのCPU割り当ての合計は、4 vCPUに対して意図的に4.75としています。割り当ては上限であって予約ではなく、各サービスが同時にピークになることはないためです。

## 知っておくと良いこと

- **パスワードと鍵は変更しないでください。** `POSTGRES_PASSWORD`は初回起動時にデータボリュームに焼き込まれます — 後から変更すると、データベースが孤立します。`JWT_SECRET`はセッションに署名します。変更すると全ユーザーがログアウトされます。インストーラーは、再実行のたびに両方を保持します。
- **`COMPOSE_PROJECT_NAME=klacks`**は固定されており、ホストとアップデートサービスがフォルダー名に関係なく同じComposeプロジェクトを指すようにしています。インストール後は変更しないでください。
- **`KnowledgeIndex__WarmupEnabled=false`はメモリ節約のオプションではありません。** 検索の構築を起動時から最初のチャット要求へ移すだけで、常時運用ではセッションは同じように存在します。ホストが起動時にメモリ不足で失敗する場合にのみ有効です。
- **APIインスタンスを複数にしますか?** その場合はSignalRバックプレーンが必要です。Klacksには含まれていません: RESP互換のサービスをご自身で用意し(たとえばValkey — Redisと違い、7.4以降はBSD-3でライセンスされています)、nginxテンプレートに用意されたスティッキーなアップストリーム(`ip_hash`)を有効にしてください。バックプレーンがなければ、現在のすべてのインストールと同様に`klacks-api`インスタンスは1つだけです。
- **国別プロファイル:** インストーラーは30のプロファイルを備えています: `ae`、`at`、`ch`、`cn`、`cz`、`de`、`dk`、`es`、`fi`、`fr`、`gb`、`gr`、`id`、`il`、`it`、`jp`、`kr`、`li`、`my`、`nl`、`no`、`pl`、`pt`、`ro`、`sa`、`se`、`th`、`tw`、`us`、`vn`。プロファイルは初回起動時に、言語、国/地域とタイムゾーン、祝日カレンダー、週末と週の開始日、労働時間の上限、休暇の付与日数、割増、標準の給与エクスポート先(スイスなら`abaconnect-ch`など)、そして業種テンプレートを設定します — たとえばスピテックスなら、計画ルールのテンプレート「CH Spitex Standard」です。プロファイルがなければ、Klacksは中立の状態で起動し、すべてを手動で設定します。
