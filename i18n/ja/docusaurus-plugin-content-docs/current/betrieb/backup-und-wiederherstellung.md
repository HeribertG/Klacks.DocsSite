# バックアップと復元

データはすべてお客様のインフラ上にあります — つまり、バックアップもお客様の責任です。このページでは、何をバックアップすべきか、そしてどう書き戻すかを説明します。

## バックアップが必要なもの

| 対象 | 場所 | 頻度 |
|---|---|---|
| データベース | ボリューム`postgres_data` | 毎日、少なくとも各アップデートの前 |
| アップロード | ボリューム`api-uploads` | データベースと一緒に |
| ドキュメント | ボリューム`api-documents` | データベースと一緒に |
| キーリング | ボリューム`api-dataprotection` | データベースと一緒に、**必ず** |

ボリューム`api-dataprotection`には、Klacksが暗号化された設定(たとえば通信チャネルの認証情報)を復号するためのキーリングが入っています。このキーリングのないデータベースは存在はしますが、完全には使えません — 常に一緒にバックアップしてください。

## データベースのバックアップ

```bash
docker exec klacks-postgres pg_dump -U admin -d Klacks -Fc > klacks-20260922.dump
```

`-Fc`(カスタム)形式は圧縮され、書き戻すときに個別のテーブルを選べます。

## データベースの復元

```bash
docker exec -i klacks-postgres pg_restore -U admin -d Klacks --clean --if-exists < klacks-20260922.dump
```

`--clean --if-exists`は、既存のオブジェクトを事前に削除し、すでに存在するテーブルが原因で書き戻しが失敗しないようにします。

## 落とし穴: マイグレーション失敗後のロールバック

過去に本番障害が起きたのはまさにここで、その仕組みはダンプを使うあらゆるロールバックに共通です:

不具合のあるバージョンがマイグレーションで**新しいテーブル**を作成した場合、それらのテーブルはダンプに含まれていません。そのため、書き戻してもデータベースは古い状態にはなりません — 新しいテーブルは書き戻し後も**残り**、一方でマイグレーション履歴(`__EFMigrationsHistory`)は古い状態に戻ります。次の起動でエラー`42P07: relation "…" already exists`が発生し、インストールは再起動ループに陥ります。

アップデート失敗後に手動でロールバックする場合は、書き戻した後に、古いバージョンには存在しなかったテーブルが残っていないかを確認し、APIを再起動する**前に**それらを削除してください。

## 保持と削除

Klacksは、削除フラグを付けるだけでなく、データを**物理的に**削除します。バックグラウンドサービスが毎日実行され、設定された期限より前に削除された、削除済みマークの付いた行を取り消し不能な形で削除します — しかも削除フラグを持つ**すべての**テーブルが対象です(従業員、住所、グループ、勤務、勤務時間、欠勤、休憩など)。例外リストはありません。削除義務は、復元できることよりも意図的に優先されます。

期限は設定`DATA_RETENTION_DAYS`で制御します。指定しない場合の既定値は**3650日(10年)**です。この設定の詳細は[データ保持](../../einstellungen/system-sicherheit/datenaufbewahrung/)のページにあります。

## 知っておくと良いこと

- **各アップデートの前に、Klacks自身がバックアップを取ります。** アップデートサービスは、新しいバージョンを有効にする前にデータバックアップを作成します。マイグレーションがある場合、そのバックアップはアップデート操作に紐づけられ、自動または手動のロールバックで再利用されます。これは、ご自身による**外部の**バックアップの代わりにはなりません — 外部バックアップは、ホスト自体が被害を受けた場合にこそ役立ちます。
- **バックアップを検証してください。** 一度も書き戻したことのないダンプは、バックアップではなく思い込みです。使い捨てのデータベースを作り、そこに書き戻してみてから、その手順を信頼してください。
- **キーリングはデータベースとは別に保管してください。** `api-dataprotection`が同じバックアップセットにあり、同じ事故で両方が被害を受けると、暗号化は意味を失います。
