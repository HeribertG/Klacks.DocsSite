# トラブルシューティング

Klacksが期待どおりに動かないとき、たいていは疑わしい2つのサービスのログを確認することと、プロセスが本当にまだ動いているかを確かめることが解決への道です。

## まず: 何が動いているかを確認する

```bash
docker compose ps
docker compose logs klacks-api
docker compose logs klacks-updater
```

`docker compose ps`は、どのサービスが動いていて正常かを示します。`klacks-api`は、起動、マイグレーション、データベースへの初期データ投入を書き出します。`klacks-updater`は、アップデートの検出、バックアップ、切り替え、ロールバックを書き出します。

## 古いログは証拠にならない

すでに時間を無駄にしたことのある落とし穴です: ログファイルは**以前の**起動のものかもしれません。そこでエラーを見つけて現在のエラーだと思い込むと、探す場所を間違えます。

そのため、ログが**まだ増えているか**を確認してください:

```bash
wc -c klacks-api.log; sleep 10; wc -c klacks-api.log
```

サイズが変わらない(増加が0バイト)なら、そのプロセスはもう書き込んでいません — ログに何が書かれていても、動いていないということです。信頼できる根拠になるのは、確実に追記されているログで、エラーをあらためて再現させた場合だけです。

## よくあるメッセージとその意味

| メッセージ | 意味 | 対処 |
|---|---|---|
| `no matching manifest for linux/amd64` | お使いのアーキテクチャ向けのイメージが存在しません | 開発元がイメージをマルチアーキテクチャ(amd64**と**arm64)で公開する必要があります |
| `pull access denied` | パッケージレジストリ上のパッケージが非公開です | 認証情報付きでインストールをやり直します: Windowsでは`-GhcrUser`/`-GhcrToken`、Linuxでは`GHCR_USER`/`GHCR_TOKEN` |
| `errorCode: SETUP_REQUIRED`、HTTP `403` | 管理者セットアップゲートが有効です | `admin@test.com`でログインし、自分の管理者アカウントを作成します — [インストールとPlayground](../../erste-schritte/installation-und-playground/)を参照 |
| コンテナがマネージドのスタックトレースなしで終了コード`-1`(`0xffffffff`)で終了する | C/C++ライブラリ内の**ネイティブ**クラッシュで、C#の`try/catch`では捕捉できません | コンテナの**stderr**出力を確認します — 本当の原因はアプリケーションログではなくそこにあります |
| アプリケーションエラーがログにないのにコンテナが終了する | メモリ不足のためカーネルがプロセスを終了させました(OOM) | メモリ上限を確認します — [システム要件](../systemvoraussetzungen/)を参照 |
| 失敗したアップデート後の`42P07: relation "…" already exists` | マイグレーションが作成したテーブルを、書き戻しが削除しませんでした | [バックアップと復元](../backup-und-wiederherstellung/)の落とし穴を参照 |
| `Application started`の数秒後にAPIが停止する | 起動は成功し、クラッシュはその後に起きます — ネイティブライブラリに典型的です | 終了コード`-1`と同じ手がかり: アプリケーションログではなくstderrを確認 |

**Windows on ARMのマシン**(Snapdragon X)では、ローカルで動く検索が過去にまさにこのようなネイティブライブラリで失敗しました: APIは`Application started`と報告したのに、数秒後には画面から到達できなくなったのです。ARM版Windowsのホストでこのパターンを見たら、最初に見るべきはコンソール出力です(ファイルログではありません) — 該当するCPU検出のメッセージが表示されたのはそこでした。

## 不具合の切り分け方

1. **正確に何をしましたか**、そして何を期待していましたか? エラー直前の操作が答えの半分です。
2. **どのサービスが動いていますか?** `docker compose ps`。
3. **ログはまだ増えていますか?** 上記を参照。
4. **stderrの最後には何がありましたか?** ネイティブのクラッシュでは唯一の情報源です。
5. **最近何が変わりましたか?** アップデート、設定、新しい証明書。

## 知っておくと良いこと

- **早期に起動したサービスと正常なサービスは、ログ上では同じに見えます。** 画面に何も届かないときは、プロセスがそもそもまだ動いているかを確認してください — 最後に何を書き込んだかだけでなく。
- **アプリケーションエラーなしのクラッシュでは、まずメモリを疑ってください。** 特に、新しい検索モデルを含むアップデートの後はそうです。
- **報告に役立つ情報:** 対象のバージョン(`.env`の`KLACKS_API_TAG`/`KLACKS_UI_TAG`)、`docker compose ps`の出力、両方のログの最後の数行、エラー直前の操作。`.env`のパスワードやキーは**含めないで**ください。
