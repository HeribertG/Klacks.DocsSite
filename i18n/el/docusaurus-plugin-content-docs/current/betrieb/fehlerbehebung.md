# Αντιμετώπιση προβλημάτων

Όταν το Klacks δεν κάνει ό,τι πρέπει, ο δρόμος περνά σχεδόν πάντα από τα αρχεία καταγραφής των δύο ύποπτων υπηρεσιών — και από το ερώτημα αν η διεργασία πράγματι εξακολουθεί να τρέχει.

## Πρώτα: δείτε τι τρέχει

```bash
docker compose ps
docker compose logs klacks-api
docker compose logs klacks-updater
```

Το `docker compose ps` δείχνει ποιες υπηρεσίες τρέχουν και αν είναι υγιείς. Το `klacks-api` καταγράφει την εκκίνηση, τη μετάβαση (migration) και την πλήρωση της βάσης δεδομένων· το `klacks-updater` καταγράφει την ανίχνευση, το αντίγραφο ασφαλείας, την εναλλαγή και τη διαδρομή επιστροφής μιας ενημέρωσης.

## Ένα παλιό αρχείο καταγραφής δεν αποτελεί απόδειξη

Μια παγίδα που έχει ήδη κοστίσει χρόνο: το αρχείο καταγραφής μπορεί να προέρχεται από **προηγούμενη** εκκίνηση. Όποιος βρει σε αυτό ένα σφάλμα και το θεωρήσει τρέχον, ψάχνει σε λάθος σημείο.

Ελέγξτε γι' αυτό αν το αρχείο καταγραφής **εξακολουθεί να μεγαλώνει**:

```bash
wc -c klacks-api.log; sleep 10; wc -c klacks-api.log
```

Αν το μέγεθος παραμένει ίδιο (αύξηση 0 byte), η διεργασία δεν γράφει πια — δεν τρέχει, ανεξάρτητα από το τι περιέχει το αρχείο. Μόνο μια νέα επανάληψη του σφάλματος με ένα αρχείο καταγραφής που αποδεδειγμένα ενημερώνεται αποτελεί αξιόπιστη βάση.

## Συχνά μηνύματα και τι σημαίνουν

| Μήνυμα | Σημασία | Τι να κάνετε |
|---|---|---|
| `no matching manifest for linux/amd64` | Το image δεν υπάρχει για την αρχιτεκτονική σας | Ο κατασκευαστής πρέπει να δημοσιεύσει το image για πολλαπλές αρχιτεκτονικές (amd64 **και** arm64) |
| `pull access denied` | Το πακέτο στο αρχείο πακέτων είναι ιδιωτικό | Επαναλάβετε την εγκατάσταση με στοιχεία πρόσβασης: `-GhcrUser`/`-GhcrToken` σε Windows, `GHCR_USER`/`GHCR_TOKEN` σε Linux |
| `errorCode: SETUP_REQUIRED`, HTTP `403` | Το Admin-Setup-Gate είναι ενεργό | Συνδεθείτε με `admin@test.com` και δημιουργήστε τον δικό σας λογαριασμό Admin — βλ. [Εγκατάσταση και Playground](../../erste-schritte/installation-und-playground/) |
| Το container τερματίζεται χωρίς managed stacktrace με exit code `-1` (`0xffffffff`) | Μια **εγγενής** κατάρρευση σε βιβλιοθήκη C/C++ που κανένα C# `try/catch` δεν μπορεί να πιάσει | Δείτε την έξοδο του container στο **stderr** — εκεί βρίσκεται η πραγματική αιτία, όχι στο αρχείο καταγραφής της εφαρμογής |
| Το container τερματίζεται, παρότι δεν υπάρχει σφάλμα εφαρμογής στο αρχείο καταγραφής | Ο πυρήνας τερμάτισε τη διεργασία λόγω έλλειψης μνήμης (OOM) | Ελέγξτε τα όρια μνήμης — βλ. [Απαιτήσεις συστήματος](../systemvoraussetzungen/) |
| `42P07: relation "…" already exists` μετά από αποτυχημένη ενημέρωση | Ένα migration δημιούργησε πίνακες που η επαναφορά δεν αφαίρεσε | Βλ. το εμπόδιο στο [Αντίγραφα ασφαλείας και επαναφορά](../backup-und-wiederherstellung/) |
| Το API τερματίζεται δευτερόλεπτα μετά το `Application started` | Η εκκίνηση πετυχαίνει, η κατάρρευση έρχεται μετά — τυπικό για εγγενή βιβλιοθήκη | Το ίδιο ίχνος όπως με το exit code `-1`: ελέγξτε το stderr, όχι το αρχείο καταγραφής της εφαρμογής |

Σε έναν **υπολογιστή Windows on ARM** (Snapdragon X) η τοπικά τρέχουσα αναζήτηση απέτυχε στο παρελθόν ακριβώς λόγω μιας τέτοιας εγγενούς βιβλιοθήκης: το API ανέφερε `Application started`, αλλά λίγα δευτερόλεπτα αργότερα δεν ήταν πια προσβάσιμο από τη διεπαφή. Αν δείτε αυτό το μοτίβο σε host Windows ARM, το πρώτο βλέμμα στρέφεται στην έξοδο της κονσόλας (όχι στο αρχείο καταγραφής) — εκεί εμφανίστηκε το μήνυμα της ανίχνευσης του επηρεαζόμενου CPU.

## Πώς περιορίζετε ένα σφάλμα

1. **Τι ακριβώς κάνατε**, και τι περιμένατε; Το τελευταίο βήμα πριν από το σφάλμα είναι το μισό της απάντησης.
2. **Ποιες υπηρεσίες τρέχουν;** `docker compose ps`.
3. **Μεγαλώνει ακόμη το αρχείο καταγραφής;** Βλ. παραπάνω.
4. **Τι υπήρχε τελευταίο στο stderr;** Στις εγγενείς καταρρεύσεις η μοναδική πηγή.
5. **Τι άλλαξε τελευταίο;** Μια ενημέρωση, μια ρύθμιση, ένα νέο πιστοποιητικό.

## Καλό να το ξέρετε

- **Μια υπηρεσία που ξεκίνησε νωρίς και μια υγιής υπηρεσία φαίνονται ίδιες στο αρχείο καταγραφής.** Αν στη διεπαφή δεν φτάνει τίποτα, ελέγξτε αν η διεργασία εξακολουθεί να τρέχει — όχι μόνο τι έγραψε τελευταία.
- **Σε κατάρρευση χωρίς σφάλμα εφαρμογής, η μνήμη είναι η πρώτη υποψία**, ιδίως μετά από ενημέρωση με νέα μοντέλα αναζήτησης.
- **Χρήσιμα στοιχεία για μια αναφορά:** η επηρεαζόμενη έκδοση (`KLACKS_API_TAG`/`KLACKS_UI_TAG` από το `.env`), η έξοδος του `docker compose ps`, οι τελευταίες γραμμές και των δύο αρχείων καταγραφής και το τελευταίο βήμα πριν από το σφάλμα. Παρακαλούμε **χωρίς** κωδικούς και κλειδιά από το `.env`.
