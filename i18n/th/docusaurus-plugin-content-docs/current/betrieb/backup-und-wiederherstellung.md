# การสำรองข้อมูลและการกู้คืน

ข้อมูลของคุณอยู่บนโครงสร้างพื้นฐานของคุณทั้งหมด — การสำรองข้อมูลจึงเป็นความรับผิดชอบของคุณด้วย หน้านี้แสดงสิ่งที่ต้องสำรองและวิธีนำกลับมาคืน

## สิ่งที่ต้องสำรอง

| อะไร | อยู่ที่ไหน | บ่อยแค่ไหน |
|---|---|---|
| ฐานข้อมูล | วอลุ่ม `postgres_data` | ทุกวัน อย่างน้อยก่อนการอัปเดตทุกครั้ง |
| ไฟล์อัปโหลด | วอลุ่ม `api-uploads` | พร้อมกับฐานข้อมูล |
| เอกสาร | วอลุ่ม `api-documents` | พร้อมกับฐานข้อมูล |
| พวงกุญแจ | วอลุ่ม `api-dataprotection` | พร้อมกับฐานข้อมูล **จำเป็นอย่างยิ่ง** |

วอลุ่ม `api-dataprotection` เก็บพวงกุญแจที่ Klacks ใช้ถอดรหัสการตั้งค่าที่เข้ารหัสไว้ (เช่น ข้อมูลเข้าสู่ระบบของช่องทางสื่อสาร) ฐานข้อมูลที่ไม่มีพวงกุญแจนี้แม้จะยังอยู่ แต่ใช้งานได้ไม่สมบูรณ์ — ให้สำรองมันไปด้วยเสมอ

## การสำรองฐานข้อมูล

```bash
docker exec klacks-postgres pg_dump -U admin -d Klacks -Fc > klacks-20260922.dump
```

รูปแบบ `-Fc` (custom) บีบอัดข้อมูลและช่วยให้เลือกกู้คืนเฉพาะบางตารางได้

## การกู้คืนฐานข้อมูล

```bash
docker exec -i klacks-postgres pg_restore -U admin -d Klacks --clean --if-exists < klacks-20260922.dump
```

`--clean --if-exists` จะลบออบเจ็กต์ที่มีอยู่ก่อน เพื่อไม่ให้การกู้คืนล้มเหลวเพราะตารางที่มีอยู่แล้ว

## จุดสะดุด: การย้อนกลับหลังการย้ายข้อมูลที่ล้มเหลว

ที่นี่เองที่ระบบ production เคยล่มในอดีต และกลไกนี้เป็นกลไกของการย้อนกลับด้วยดัมพ์ทุกแบบ:

หากเวอร์ชันที่บกพร่องสร้าง**ตารางใหม่**ผ่านการย้ายข้อมูล (migration) ตารางเหล่านั้นจะไม่อยู่ในดัมพ์ เมื่อกู้คืน ฐานข้อมูลจึงไม่ได้กลับไปอยู่ในสถานะเดิม — ตารางใหม่**ยังคงอยู่รอด**หลังการกู้คืน ในขณะที่ประวัติการย้ายข้อมูล (`__EFMigrationsHistory`) ถูกตั้งกลับไปเป็นสถานะเดิม การพยายามเริ่มระบบครั้งถัดไปจึงชนกับข้อผิดพลาด `42P07: relation "…" already exists` และการติดตั้งจะค้างอยู่ในวงจรเริ่มใหม่ไม่รู้จบ

หากคุณย้อนกลับด้วยตนเองหลังการอัปเดตที่ล้มเหลว ให้ตรวจสอบหลังการกู้คืนว่ามีตารางตกค้างที่เวอร์ชันเก่ายังไม่มีหรือไม่ และลบตารางเหล่านั้น**ก่อน**จะเริ่ม API อีกครั้ง

## การเก็บรักษาและการลบ

Klacks ไม่ได้ลบข้อมูลแค่ด้วยเครื่องหมายการลบ แต่ลบ**ทางกายภาพ** บริการเบื้องหลังทำงานทุกวันและลบแถวทั้งหมดที่ถูกทำเครื่องหมายว่าลบแล้วและเวลาที่ลบเกินระยะเวลาที่กำหนดไว้ออกอย่างถาวร — ครอบคลุม**ทุก**ตารางที่มีเครื่องหมายการลบ (พนักงาน ที่อยู่ กลุ่ม กะงาน เวลาทำงาน การขาดงาน การพัก และอื่น ๆ) ไม่มีรายการข้อยกเว้น ภาระหน้าที่ในการลบถูกให้ความสำคัญเหนือความสามารถในการกู้คืนโดยตั้งใจ

คุณควบคุมระยะเวลาผ่านการตั้งค่า `DATA_RETENTION_DAYS` หากไม่ได้ระบุเอง จะใช้ค่าเริ่มต้น **3650 วัน (10 ปี)** หน้า[การเก็บรักษาข้อมูล](../../einstellungen/system-sicherheit/datenaufbewahrung/)อธิบายการตั้งค่านี้โดยละเอียด

## ข้อมูลที่ควรทราบ

- **Klacks สำรองข้อมูลให้เองก่อนการอัปเดตทุกครั้ง** บริการอัปเดตสร้างข้อมูลสำรองก่อนเปิดใช้เวอร์ชันใหม่ เมื่อมีการย้ายข้อมูล ข้อมูลสำรองจะผูกกับการอัปเดตนั้นและถูกนำกลับมาใช้ซ้ำสำหรับการย้อนกลับอัตโนมัติหรือด้วยตนเอง สิ่งนี้ไม่ได้ทดแทนการสำรองข้อมูล**ภายนอก**ของคุณเอง — การสำรองนั้นป้องกันกรณีที่ตัวโฮสต์เองได้รับผลกระทบพอดี
- **ตรวจสอบข้อมูลสำรองของคุณ** ดัมพ์ที่ไม่เคยถูกกู้คืนเป็นเพียงข้อสันนิษฐาน ไม่ใช่ข้อมูลสำรอง ให้สร้างฐานข้อมูลทิ้งขว้างแล้วกู้คืนลงไปที่นั่นก่อนจะพึ่งพาวิธีนี้
- **เก็บพวงกุญแจแยกจากฐานข้อมูล** หาก `api-dataprotection` อยู่ในชุดสำรองเดียวกัน และเหตุการณ์เดียวกันกระทบทั้งสองอย่าง การเข้ารหัสก็ไร้ค่า
