# การแก้ไขปัญหา

เมื่อ Klacks ไม่ทำงานอย่างที่ควรจะเป็น ทางออกเกือบทุกครั้งจะผ่านบันทึกของสองบริการที่น่าสงสัย — และผ่านคำถามว่ากระบวนการนั้นยังทำงานอยู่จริงหรือไม่

## ขั้นแรก: ดูว่าอะไรกำลังทำงานอยู่

```bash
docker compose ps
docker compose logs klacks-api
docker compose logs klacks-updater
```

`docker compose ps` แสดงว่าบริการใดกำลังทำงานและอยู่ในสภาพปกติหรือไม่ `klacks-api` เขียนบันทึกการเริ่มต้น การย้ายข้อมูล และการเติมข้อมูลลงฐานข้อมูล ส่วน `klacks-updater` เขียนบันทึกการตรวจพบ การสำรองข้อมูล การสลับเวอร์ชัน และเส้นทางย้อนกลับของการอัปเดต

## บันทึกเก่าไม่ใช่หลักฐาน

กับดักที่เคยทำให้เสียเวลามาแล้ว: ไฟล์บันทึกอาจมาจากการเริ่มต้น**ครั้งก่อน** ผู้ที่พบข้อผิดพลาดในนั้นแล้วคิดว่าเป็นข้อผิดพลาดปัจจุบันกำลังค้นหาผิดที่

ดังนั้นให้ตรวจสอบว่าบันทึก**ยังเพิ่มขึ้นอยู่หรือไม่**:

```bash
wc -c klacks-api.log; sleep 10; wc -c klacks-api.log
```

หากขนาดคงเดิม (เพิ่มขึ้น 0 ไบต์) แสดงว่ากระบวนการไม่ได้เขียนอีกต่อไป — มันไม่ได้ทำงาน ไม่ว่าในบันทึกจะเขียนอะไรไว้ก็ตาม ต่อเมื่อเกิดข้อผิดพลาดซ้ำใหม่พร้อมบันทึกที่พิสูจน์ได้ว่ายังทำงานอยู่ จึงจะเป็นพื้นฐานที่เชื่อถือได้

## ข้อความที่พบบ่อยและความหมาย

| ข้อความ | ความหมาย | ต้องทำอะไร |
|---|---|---|
| `no matching manifest for linux/amd64` | ไม่มีอิมเมจสำหรับสถาปัตยกรรมของคุณ | ผู้พัฒนาต้องเผยแพร่อิมเมจแบบหลายสถาปัตยกรรม (amd64 **และ** arm64) |
| `pull access denied` | แพ็กเกจในคลังแพ็กเกจเป็นแบบส่วนตัว | ติดตั้งซ้ำพร้อมข้อมูลเข้าสู่ระบบ: `-GhcrUser`/`-GhcrToken` บน Windows, `GHCR_USER`/`GHCR_TOKEN` บน Linux |
| `errorCode: SETUP_REQUIRED`, HTTP `403` | ด่านตั้งค่า Admin กำลังทำงานอยู่ | เข้าสู่ระบบด้วย `admin@test.com` และสร้างบัญชี Admin ของคุณเอง — ดู[การติดตั้งและ Playground](../../erste-schritte/installation-und-playground/) |
| คอนเทนเนอร์จบการทำงานโดยไม่มี managed stack trace พร้อมรหัสออก `-1` (`0xffffffff`) | การขัดข้องแบบ **เนทีฟ** ในไลบรารี C/C++ ซึ่ง `try/catch` ของ C# ดักไม่ได้ | ดูเอาต์พุตของคอนเทนเนอร์บน **stderr** — สาเหตุที่แท้จริงอยู่ที่นั่น ไม่ได้อยู่ในบันทึกของแอปพลิเคชัน |
| คอนเทนเนอร์ถูกยุติทั้งที่ไม่มีข้อผิดพลาดของแอปพลิเคชันในบันทึก | เคอร์เนลยุติกระบวนการเพราะหน่วยความจำไม่พอ (OOM) | ตรวจสอบขีดจำกัดหน่วยความจำ — ดู[ความต้องการของระบบ](../systemvoraussetzungen/) |
| `42P07: relation "…" already exists` หลังการอัปเดตที่ล้มเหลว | การย้ายข้อมูลสร้างตารางไว้ซึ่งการกู้คืนไม่ได้ลบออก | ดูจุดสะดุดที่[การสำรองข้อมูลและการกู้คืน](../backup-und-wiederherstellung/) |
| API ตายไม่กี่วินาทีหลัง `Application started` | การเริ่มต้นสำเร็จ แต่การขัดข้องเกิดขึ้นหลังจากนั้น — ลักษณะเฉพาะของไลบรารีเนทีฟ | แนวทางเดียวกับรหัสออก `-1`: ตรวจสอบ stderr ไม่ใช่บันทึกของแอปพลิเคชัน |

บน**เครื่อง Windows-on-ARM** (Snapdragon X) การค้นหาที่ทำงานในเครื่องเคยล้มเหลวในอดีตที่ไลบรารีเนทีฟลักษณะนี้พอดี: API รายงาน `Application started` แต่ไม่กี่วินาทีต่อมาหน้าจอใช้งานก็เข้าถึงไม่ได้อีก หากคุณเห็นรูปแบบนี้บนโฮสต์ ARM-Windows ให้ดูที่เอาต์พุตของคอนโซล (ไม่ใช่บันทึกในไฟล์) เป็นอันดับแรก — ข้อความจากการตรวจจับ CPU ที่ได้รับผลกระทบปรากฏอยู่ที่นั่น

## วิธีจำกัดขอบเขตข้อผิดพลาด

1. **คุณทำอะไรไปกันแน่** และคุณคาดหวังอะไร? ขั้นตอนสุดท้ายก่อนเกิดข้อผิดพลาดคือครึ่งหนึ่งของคำตอบ
2. **บริการใดกำลังทำงานอยู่?** `docker compose ps`
3. **บันทึกยังเพิ่มขึ้นอยู่หรือไม่?** ดูด้านบน
4. **อะไรอยู่บน stderr เป็นรายการสุดท้าย?** สำหรับการขัดข้องแบบเนทีฟ นี่เป็นแหล่งเดียว
5. **มีอะไรเปลี่ยนแปลงล่าสุด?** การอัปเดต การตั้งค่า ใบรับรองใหม่

## ข้อมูลที่ควรทราบ

- **บริการที่เริ่มต้นไปแล้วและบริการที่ปกติดีดูเหมือนกันในบันทึก** หากไม่มีอะไรไปถึงหน้าจอใช้งาน ให้ตรวจสอบว่ากระบวนการยังทำงานอยู่เลยหรือไม่ — ไม่ใช่แค่ดูว่ามันเขียนอะไรไว้ล่าสุด
- **เมื่อเกิดการขัดข้องโดยไม่มีข้อผิดพลาดของแอปพลิเคชัน หน่วยความจำคือผู้ต้องสงสัยอันดับแรก** โดยเฉพาะหลังการอัปเดตที่มาพร้อมโมเดลค้นหาใหม่
- **ข้อมูลที่เป็นประโยชน์สำหรับการแจ้งปัญหา:** เวอร์ชันที่ได้รับผลกระทบ (`KLACKS_API_TAG`/`KLACKS_UI_TAG` จาก `.env`) เอาต์พุตของ `docker compose ps` บรรทัดสุดท้ายของบันทึกทั้งสองไฟล์ และขั้นตอนสุดท้ายก่อนเกิดข้อผิดพลาด โปรด**อย่า**ใส่รหัสผ่านและกุญแจจาก `.env`
