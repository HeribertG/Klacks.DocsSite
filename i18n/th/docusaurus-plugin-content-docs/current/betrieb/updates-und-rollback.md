# การอัปเดตและการย้อนกลับ

Klacks อัปเดตตัวเอง — ด้วยแพ็กเกจที่มีลายเซ็น การสำรองข้อมูลก่อนทุกขั้นตอน และเส้นทางย้อนกลับอัตโนมัติเมื่อมีสิ่งผิดพลาด หน้านี้อธิบายว่าเกิดอะไรขึ้นและคุณแทรกแซงได้อย่างไร

## การอัปเดตทำงานอย่างไร

1. **ตรวจพบ** API สอบถาม manifest ที่มีลายเซ็นซึ่งผู้พัฒนาเผยแพร่พร้อมกับทุกรุ่น หากมีเวอร์ชันที่ใหม่กว่าบันทึกอยู่ที่นั่น การอัปเดตจะถือว่าพร้อมใช้งาน
2. **สำรองข้อมูล** บริการอัปเดตสร้างข้อมูลสำรองของฐานข้อมูล หากเวอร์ชันใหม่มีการย้ายข้อมูล (migration) ข้อมูลสำรองนี้จะถูกผูกกับกระบวนการอัปเดตอย่างถาวรและพร้อมสำหรับเส้นทางย้อนกลับในภายหลัง
3. **ดึงและเปิดใช้งานพร้อมกัน** บริการดาวน์โหลดอิมเมจใหม่ของ `klacks-api` **และ** `klacks-ui` แล้วสลับทั้งสองพร้อมกัน — ทั้งสองส่วนทำงานเข้าจังหวะกัน ไม่เคยอยู่คนละเวอร์ชัน
4. **ตรวจสอบ** หลังการสลับ บริการสอบถามการตรวจสอบสถานะเชิงลึก `/internal/health/deep`
5. **ประเมินผล** หากเวอร์ชันใหม่ปกติดี การอัปเดตถือว่าสำเร็จ หากไม่ บริการจะย้อนกลับ**ทั้งสองส่วน**ไปยังเวอร์ชันก่อนหน้าโดยอัตโนมัติและตรวจสอบอีกครั้ง หากสิ่งนั้นก็ไม่สำเร็จ สถานะจะถูกบันทึกเป็นล้มเหลวเพื่อให้คุณมองเห็น

## "มีลายเซ็น" หมายความว่าอย่างไร

ผู้พัฒนาลงนามทุกรุ่น และ Klacks ของคุณจะตรวจสอบลายเซ็นก่อนยอมรับแพ็กเกจ กุญแจสาธารณะและที่อยู่ของ manifest เป็นค่าคงที่ของผู้พัฒนาใน `.env` ของคุณ:

- `UPDATE_MANIFEST_BASE_URL` — ตั้งตายตัวไปที่แหล่งเผยแพร่รุ่นของผู้พัฒนา
- `UPDATE_SIGNATURE_PUBLIC_KEY` — ต้องตรงกับกุญแจส่วนตัวที่ผู้พัฒนาใช้ลงนาม

ค่าสองตัวนี้ **ไม่ได้มีไว้ให้เปลี่ยน** ผู้ที่เปลี่ยนค่าเหล่านี้จะยกเลิกการตรวจสอบ และเปิดช่องโหว่ที่ลายเซ็นปิดไว้พอดี

Manifest มีข้อมูลต่าง ๆ เช่น ช่องทาง (`Stable` หรือ `Beta`) เวอร์ชันล่าสุด เวอร์ชันขั้นต่ำที่สามารถอัปเดตโดยตรงได้ (`MinUpgradableFrom`) วันที่เผยแพร่ มีการย้ายข้อมูลฐานข้อมูลรวมอยู่ด้วยหรือไม่ อาร์ติแฟกต์ ลายเซ็น และลิงก์ไปยังรายการการเปลี่ยนแปลง

`klacks-api` และ `klacks-ui` ถูก**ปักหมุดไว้ที่เวอร์ชันที่ระบุแน่นอน**ใน `.env` เพื่อไม่ให้ทั้งสองแยกจากกันโดยไม่รู้ตัว ตัวบริการอัปเดตเองทำงานที่ `latest` เสมอ — โดยตั้งใจให้ไม่อยู่ใน manifest ที่มีลายเซ็น และสลับเฉพาะ api กับ ui

## การตั้งค่าระหว่างการใช้งาน

ในพื้นที่ Admin ที่ **ระบบ → การอัปเดต**:

| การตั้งค่า | ผล |
|---|---|
| **เปิดใช้งานการอัปเดตอัตโนมัติ** | ตรวจพบและติดตั้งการอัปเดตโดยอัตโนมัติ |
| **แจ้งเตือนเท่านั้น** | การอัปเดตจะถูก**ตรวจพบ**เท่านั้น แต่ไม่ถูกติดตั้งจนกว่าคุณจะสั่ง |
| **ช่วงเวลาบำรุงรักษา** | ช่วงเวลาที่อนุญาตให้การอัปเดตอัตโนมัติทำงาน |

การตั้งค่าเหล่านี้เก็บอยู่ในฐานข้อมูลและมีผลเหนือกว่าค่าเริ่มต้นจาก `.env` (`UPDATE_AUTO_ENABLED`, `UPDATE_NOTIFY_ONLY`) ซึ่งมีผลเฉพาะตอนเริ่มต้นครั้งแรก

## การย้อนกลับด้วยตนเอง

โดยอัตโนมัติ ไม่มีใครต้องแทรกแซงที่นี่ — บริการจะย้อนกลับการอัปเดตที่ล้มเหลวเอง หากคุณตั้งใจจะถอยกลับหนึ่งขั้น:

1. ตั้ง `KLACKS_API_TAG` และ `KLACKS_UI_TAG` ใน `.env` เป็นเวอร์ชันก่อนหน้า
2. เปิดใช้งานสแต็กใหม่: `docker compose up -d klacks-api klacks-ui`
3. **หากเวอร์ชันที่บกพร่องได้ย้ายข้อมูลไปแล้ว** ให้กู้คืนข้อมูลสำรองที่ตรงกันจากก่อนการอัปเดตเพิ่มเติมด้วย — และโปรดสังเกตจุดสะดุดในหน้า[การสำรองข้อมูลและการกู้คืน](../backup-und-wiederherstellung/): ตารางที่เวอร์ชันใหม่สร้างขึ้นจะอยู่รอดหลังการกู้คืนและขวางการเริ่มต้นครั้งถัดไป

## ข้อมูลที่ควรทราบ

- **เส้นทางย้อนกลับไม่ใช่ทางออกฉุกเฉิน แต่เป็นกรณีปกติ** ทุกกระบวนการอัปเดตมีสถานะ: สำเร็จ ย้อนกลับแล้ว หรือเส้นทางย้อนกลับล้มเหลว การอัปเดตที่ย้อนกลับแล้วเป็นกระบวนการปกติที่มีการบันทึก — ไม่ใช่เหตุขัดข้อง
- **การอัปเดตที่ย้อนกลับแล้วไม่ใช่การรีเซ็ต** การย้อนกลับคืนเวอร์ชัน ไม่ใช่ข้อมูลของคุณ การเปลี่ยนแปลงข้อมูลที่คุณทำระหว่างการอัปเดตกับการย้อนกลับจะมาจากสถานะของข้อมูลสำรอง
- **คุณตรวจสอบได้ในบันทึก:** `docker compose logs klacks-updater` แสดงการตรวจพบ การสำรองข้อมูล การสลับเวอร์ชัน และเส้นทางย้อนกลับ
