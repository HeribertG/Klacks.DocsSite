# 시스템 요구 사항과 구성

Klacks는 사용자의 서버에서 Docker 스택으로 실행됩니다. 이 페이지는 어떤 서비스가 시작되는지, 그리고 호스트를 어떻게 산정하는지를 권장값의 근거가 된 측정값과 함께 설명합니다.

## 구성: 다섯 개의 서비스

온프레미스 패키지는 운영에 필요한 것만 시작합니다:

| 서비스 | 이미지 | 역할 |
|---|---|---|
| `klacks-postgres` | `pgvector/pgvector:pg17` | 데이터베이스. 벡터 확장이 이미 포함되어 있습니다 |
| `klacks-api` | `ghcr.io/heribertg/klacks-api` | 백엔드. 시작 시 데이터베이스를 마이그레이션하고 초기 데이터를 채웁니다 |
| `klacks-ui` | `ghcr.io/heribertg/klacks-ui` | Angular 화면. nginx를 통해 제공됩니다 |
| `klacks-updater` | `ghcr.io/heribertg/klacks-updater` | 서명된 업데이트를 적용합니다(api와 ui를 함께) |
| `klacks-proxy` | `nginx:alpine` | TLS 종단 및 리버스 프록시 |

제조사의 내부 서비스(개발용 지식 저장소, 마케팅, 마켓플레이스, pgAdmin, certbot, Blazor 화면)는 의도적으로 포함되어 있지 **않습니다**. 운영자는 자신의 스택만 보게 됩니다.

## 호스트가 갖춰야 할 것

- 최소 **RAM 8 GB와 4 vCPU**(아래 계산 참조).
- Docker Desktop(Windows/macOS) 또는 Compose v2가 포함된 Docker Engine(Linux), **amd64 또는 arm64**.
- 사용 가능한 포트 **80과 443** — `HTTP_PORT`와 `HTTPS_PORT`로 변경할 수 있습니다.
- `ghcr.io`(이미지)와 `github.com`(서명된 업데이트 매니페스트)에 대한 **아웃바운드** HTTPS 접근.
- 선택 사항: 마켓플레이스의 국가 패키지와 언어 플러그인을 위한 `klacks-software.ch:7553` 접근.

## 메모리: 왜 8 GB인지, 더 작은 호스트에서는 어떻게 되는지

Klacks는 두 개의 검색 모델(임베더와 리랭커)을 `klacks-api` 프로세스 **내부에서 로컬로** 실행합니다. 두 ONNX 세션은 상시 메모리에 유지되며, 질문마다 언로드되지 않습니다.

제조사의 운영 호스트에서 2026년 9월 12일에 측정한 값:

- 프로세스 기본 부하: 약 1'017 MB
- 임베더: 약 1'171 MB
- 리랭커: 약 116 MB
- 합계: 약 **2'304 MB** 수준에서 안정
- 2'560 MB 제한에서는 커널이 2'471 MB에서 컨테이너를 종료했습니다(OOM).

그래서 기본 제공 Compose는 `klacks-api`에 **3'584M**과 3.0 CPU를 설정하고, 유휴 시 언로드는 꺼 둡니다. 스택 전체로 계산하면: 3'584M(api) + 2'048M(postgres) + 3 × 256M(ui, updater, proxy) = **6'400 MiB**이며, 8 GB 중 나머지는 운영체제와 파일 캐시를 위해 남습니다.

**더 작은 호스트, 예를 들어 `klacks-api`에 약 3 GB인 경우:** `.env`에 다음 **두 줄을 모두** 설정하십시오 — 메모리 줄만 단독으로 설정해서는 안 됩니다:

```bash
KLACKS_API_MEMORY_LIMIT=2560M
KLACKS_API_IDLE_UNLOAD_MINUTES=30
```

유휴 시 언로드는 30분 동안 접근이 없으면 세션을 해제합니다. 그 대가로, 그 뒤의 다음 질문에서 세션을 다시 로드합니다(임베더 약 2.2~2.9초, 리랭커 약 1.1초). 1에서 5 사이의 값은 5로 올려지며, `0`은 언로드하지 않음을 뜻합니다.

## CPU: 코어가 적으면 느려질 뿐, 망가지지는 않습니다

검색은 코어가 적어도 동작하지만 느려집니다 — 연산이 가장 많은 단계는 리랭커입니다. 측정값: 후보 25개에 대해 3.0 CPU에서는 2'994~3'163 ms, 1.5 CPU에서는 4'339~4'860 ms였고, 후자에서는 서비스가 추가로 7.15초 동안 스로틀링되었습니다. 더 작은 호스트라면:

```bash
KLACKS_API_CPU_LIMIT=1.5
```

스택의 CPU 할당량은 4 vCPU에 대해 합계가 4.75가 되도록 의도적으로 잡았습니다. 할당량은 상한일 뿐 예약이 아니며, 서비스들이 동시에 최고 부하에 이르지 않기 때문입니다.

## 알아두면 좋은 점

- **비밀번호와 키는 그대로 유지하십시오.** `POSTGRES_PASSWORD`는 첫 시작 시 데이터 볼륨에 고정됩니다 — 나중에 바꾸면 데이터베이스에 접근할 수 없게 됩니다. `JWT_SECRET`은 세션에 서명하며, 바꾸면 모든 사용자가 로그아웃됩니다. 설치 프로그램은 다시 실행할 때마다 두 값을 모두 보존합니다.
- **`COMPOSE_PROJECT_NAME=klacks`**는 호스트와 업데이트 서비스가 폴더 이름과 관계없이 같은 Compose 프로젝트를 가리키도록 고정되어 있습니다. 설치 후에는 더 이상 바꾸지 마십시오.
- **`KnowledgeIndex__WarmupEnabled=false`는 메모리 절약 옵션이 아닙니다.** 검색 구축 시점을 시작 단계에서 첫 번째 채팅 요청으로 미룰 뿐이며, 상시 운영에서는 세션이 동일하게 존재합니다. 호스트가 시작할 때 메모리 부족으로 실패하는 경우에만 유용합니다.
- **API 인스턴스를 둘 이상 쓰시나요?** 그렇다면 SignalR 백플레인이 필요합니다. Klacks에는 포함되어 있지 않습니다: RESP 호환 서비스를 직접 준비하고(예: Valkey — Redis와 달리 7.4부터 BSD-3 라이선스), nginx 템플릿에 준비된 스티키 업스트림(`ip_hash`)을 활성화하십시오. 백플레인이 없으면 현재의 모든 설치와 마찬가지로 `klacks-api` 인스턴스는 정확히 하나만 실행됩니다.
- **국가 프로필:** 설치 프로그램은 30개의 프로필을 지원합니다: `ae`, `at`, `ch`, `cn`, `cz`, `de`, `dk`, `es`, `fi`, `fr`, `gb`, `gr`, `id`, `il`, `it`, `jp`, `kr`, `li`, `my`, `nl`, `no`, `pl`, `pt`, `ro`, `sa`, `se`, `th`, `tw`, `us`, `vn`. 프로필은 첫 시작 시 언어, 국가/지역과 시간대, 공휴일 캘린더, 주말과 한 주의 시작일, 근로 시간 한도, 휴가 부여 일수, 할증, 기본 급여 내보내기 대상 시스템(스위스의 경우 예를 들어 `abaconnect-ch`), 그리고 업종 템플릿을 설정합니다 — 예를 들어 스피텍스에는 계획 규칙 템플릿 "CH Spitex Standard"가 있습니다. 프로필이 없으면 Klacks는 중립 상태로 시작하며 모든 것을 직접 구성합니다.
