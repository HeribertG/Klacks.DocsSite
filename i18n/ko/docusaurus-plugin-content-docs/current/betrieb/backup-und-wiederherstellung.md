# 백업 및 복원

데이터는 전부 사용자의 인프라에 있습니다 — 따라서 백업도 사용자의 몫입니다. 이 페이지는 무엇을 백업해야 하는지, 그리고 어떻게 다시 복원하는지를 보여 줍니다.

## 백업해야 할 것

| 대상 | 위치 | 주기 |
|---|---|---|
| 데이터베이스 | 볼륨 `postgres_data` | 매일, 최소한 모든 업데이트 전 |
| 업로드 | 볼륨 `api-uploads` | 데이터베이스와 함께 |
| 문서 | 볼륨 `api-documents` | 데이터베이스와 함께 |
| 키링 | 볼륨 `api-dataprotection` | 데이터베이스와 함께, **반드시** |

`api-dataprotection` 볼륨에는 Klacks가 암호화된 설정(예: 커뮤니케이션 채널의 접속 정보)을 복호화하는 데 사용하는 키링이 들어 있습니다. 이 키링이 없는 데이터베이스는 존재하긴 하지만 온전히 사용할 수 없습니다 — 항상 함께 백업하십시오.

## 데이터베이스 백업

```bash
docker exec klacks-postgres pg_dump -U admin -d Klacks -Fc > klacks-20260922.dump
```

`-Fc`(custom) 형식은 압축되며, 복원할 때 개별 테이블을 선택할 수 있습니다.

## 데이터베이스 복원

```bash
docker exec -i klacks-postgres pg_restore -U admin -d Klacks --clean --if-exists < klacks-20260922.dump
```

`--clean --if-exists`는 기존 객체를 먼저 정리하여, 이미 존재하는 테이블 때문에 복원이 실패하지 않도록 합니다.

## 함정: 마이그레이션 실패 후의 롤백

과거에 운영 장애가 발생한 지점이 바로 여기이며, 그 메커니즘은 덤프 기반 롤백이라면 모두 같습니다:

결함이 있는 버전이 마이그레이션으로 **새 테이블**을 만들었다면, 그 테이블은 덤프에 들어 있지 않습니다. 따라서 복원해도 데이터베이스가 이전 상태로 돌아가지 않습니다 — 새 테이블은 복원 후에도 **남아 있고**, 마이그레이션 이력(`__EFMigrationsHistory`)만 이전 상태로 되돌아갑니다. 다음 시작 시도에서 `42P07: relation "…" already exists` 오류가 발생하고 설치는 재시작 루프에 빠집니다.

업데이트가 실패한 뒤 수동으로 롤백할 때는, 복원 후에 이전 버전에는 없던 테이블이 남아 있지 않은지 확인하고, API를 다시 시작하기 **전에** 그 테이블을 제거하십시오.

## 보존과 삭제

Klacks는 삭제 표시만 하는 것이 아니라 데이터를 **물리적으로** 삭제합니다. 백그라운드 서비스가 매일 실행되어, 설정된 기한보다 더 오래 전에 삭제 표시가 된 행을 되돌릴 수 없게 제거합니다 — 삭제 표시가 있는 **모든** 테이블이 대상입니다(직원, 주소, 그룹, 근무, 근무 시간, 결근, 휴식 등). 예외 목록은 없으며, 삭제 의무가 복원 가능성보다 의도적으로 우선합니다.

기한은 `DATA_RETENTION_DAYS` 설정으로 제어합니다. 별도로 지정하지 않으면 기본값은 **3650일(10년)**입니다. 이 설정은 [데이터 보존](../../einstellungen/system-sicherheit/datenaufbewahrung/) 페이지에 자세히 설명되어 있습니다.

## 알아두면 좋은 점

- **모든 업데이트 전에 Klacks가 스스로 백업합니다.** 업데이트 서비스는 새 버전을 활성화하기 전에 데이터 백업을 만듭니다. 마이그레이션이 있는 경우 이 백업은 업데이트 작업에 연결되어 자동 또는 수동 롤백에 재사용됩니다. 이것이 사용자 자신의 **외부** 백업을 대신하지는 않습니다 — 외부 백업은 호스트 자체가 피해를 입은 경우를 정확히 막아 줍니다.
- **백업을 검증하십시오.** 한 번도 복원해 보지 않은 덤프는 백업이 아니라 가정입니다. 폐기용 데이터베이스를 만들어 거기에 복원해 본 뒤에 그 절차를 신뢰하십시오.
- **키링은 데이터베이스와 따로 보관하십시오.** `api-dataprotection`이 같은 백업 세트에 있고 같은 사고로 둘 다 피해를 입으면, 암호화는 의미가 없어집니다.
