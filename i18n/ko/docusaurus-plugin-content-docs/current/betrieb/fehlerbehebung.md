# 문제 해결

Klacks가 기대한 대로 동작하지 않을 때는, 거의 항상 의심되는 두 서비스의 로그를 보는 것과 프로세스가 정말 아직 실행 중인지 확인하는 것이 해결의 길입니다.

## 먼저: 무엇이 실행 중인지 확인

```bash
docker compose ps
docker compose logs klacks-api
docker compose logs klacks-updater
```

`docker compose ps`는 어떤 서비스가 실행 중이며 정상인지 보여 줍니다. `klacks-api`는 시작, 마이그레이션, 데이터베이스 초기 데이터 채우기를 기록하고, `klacks-updater`는 업데이트의 감지, 백업, 전환, 롤백을 기록합니다.

## 오래된 로그는 증거가 아니다

이미 시간을 허비하게 만든 함정이 있습니다: 로그 파일이 **이전** 시작의 것일 수 있습니다. 거기서 오류를 발견하고 현재의 오류라고 생각하면 엉뚱한 곳을 찾게 됩니다.

따라서 로그가 **아직 늘어나고 있는지** 확인하십시오:

```bash
wc -c klacks-api.log; sleep 10; wc -c klacks-api.log
```

크기가 그대로이면(증가량 0바이트) 프로세스는 더 이상 기록하지 않습니다 — 로그에 무엇이 적혀 있든 실행 중이 아닙니다. 신뢰할 수 있는 근거는, 확실히 기록이 이어지는 로그에서 오류를 새로 재현했을 때뿐입니다.

## 자주 나오는 메시지와 그 의미

| 메시지 | 의미 | 해결 방법 |
|---|---|---|
| `no matching manifest for linux/amd64` | 사용 중인 아키텍처용 이미지가 없습니다 | 제조사가 이미지를 멀티 아키텍처(amd64 **및** arm64)로 게시해야 합니다 |
| `pull access denied` | 패키지 레지스트리의 패키지가 비공개입니다 | 접속 정보를 지정해 설치를 다시 실행합니다: Windows에서는 `-GhcrUser`/`-GhcrToken`, Linux에서는 `GHCR_USER`/`GHCR_TOKEN` |
| `errorCode: SETUP_REQUIRED`, HTTP `403` | 관리자 설정 게이트가 활성화되어 있습니다 | `admin@test.com`으로 로그인하여 자신의 관리자 계정을 만듭니다 — [설치 및 Playground](../../erste-schritte/installation-und-playground/) 참조 |
| 컨테이너가 관리형 스택 트레이스 없이 종료 코드 `-1`(`0xffffffff`)로 종료됨 | C/C++ 라이브러리에서 발생한 **네이티브** 충돌로, C#의 `try/catch`로는 잡을 수 없습니다 | 컨테이너의 **stderr** 출력을 확인합니다 — 실제 원인은 애플리케이션 로그가 아니라 그곳에 있습니다 |
| 로그에 애플리케이션 오류가 없는데 컨테이너가 종료됨 | 메모리 부족으로 커널이 프로세스를 종료했습니다(OOM) | 메모리 한도를 확인합니다 — [시스템 요구 사항](../systemvoraussetzungen/) 참조 |
| 실패한 업데이트 후 `42P07: relation "…" already exists` | 마이그레이션이 만든 테이블이 복원 과정에서 제거되지 않았습니다 | [백업 및 복원](../backup-und-wiederherstellung/)의 함정 항목 참조 |
| `Application started` 몇 초 뒤에 API가 종료됨 | 시작은 성공하고 충돌은 그 후에 발생합니다 — 네이티브 라이브러리에서 전형적입니다 | 종료 코드 `-1`일 때와 같은 단서: 애플리케이션 로그가 아니라 stderr를 확인 |

**Windows on ARM 기기**(Snapdragon X)에서는 로컬에서 실행되는 검색이 과거에 바로 이런 네이티브 라이브러리 때문에 실패한 적이 있습니다: API는 `Application started`라고 보고했지만, 몇 초 뒤에는 화면에서 접근할 수 없게 되었습니다. ARM 기반 Windows 호스트에서 이 패턴이 보이면, 가장 먼저 콘솔 출력(파일 로그가 아닙니다)을 확인하십시오 — 해당 CPU 감지 메시지는 그곳에 나타났습니다.

## 오류를 좁히는 방법

1. **정확히 무엇을 했고**, 무엇을 기대했습니까? 오류 직전의 마지막 단계가 답의 절반입니다.
2. **어떤 서비스가 실행 중입니까?** `docker compose ps`.
3. **로그가 아직 늘어나고 있습니까?** 위를 참조하십시오.
4. **stderr의 마지막 내용은 무엇이었습니까?** 네이티브 충돌의 경우 유일한 정보원입니다.
5. **최근에 무엇이 바뀌었습니까?** 업데이트, 설정, 새 인증서.

## 알아두면 좋은 점

- **일찍 시작된 서비스와 정상 서비스는 로그에서 똑같이 보입니다.** 화면에 아무것도 도착하지 않으면, 프로세스가 마지막에 무엇을 기록했는지만이 아니라 아직 실행 중인지부터 확인하십시오.
- **애플리케이션 오류 없이 충돌했다면 가장 먼저 메모리를 의심하십시오.** 특히 새로운 검색 모델이 포함된 업데이트 직후에는 그렇습니다.
- **문의 시 도움이 되는 정보:** 해당 버전(`.env`의 `KLACKS_API_TAG`/`KLACKS_UI_TAG`), `docker compose ps`의 출력, 두 로그의 마지막 몇 줄, 오류 직전의 마지막 단계. `.env`의 비밀번호와 키는 **포함하지 마십시오**.
