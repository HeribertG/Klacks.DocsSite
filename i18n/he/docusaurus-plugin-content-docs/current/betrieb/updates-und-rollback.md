# עדכונים וחזרה לאחור

Klacks מתעדכנת בעצמה — עם חבילות חתומות, גיבוי לפני כל צעד וחזרה אוטומטית לאחור כאשר משהו משתבש. עמוד זה מסביר מה קורה בדרך ואיך אפשר להתערב.

## איך עדכון מתנהל

1. **זיהוי.** ה-API שואלת את המניפסט החתום שהיצרן מפרסם עם כל Release. אם רשומה שם גרסה חדשה יותר, העדכון נחשב זמין.
2. **גיבוי.** שירות העדכונים יוצר גיבוי נתונים של מסד הנתונים. אם הגרסה החדשה כוללת מיגרציה, הגיבוי נקשר באופן קבוע לפעולת העדכון וממתין בהמשך לדרך חזרה.
3. **משיכה והפעלה משותפת.** השירות מוריד את התמונות החדשות עבור `klacks-api` **ו**-`klacks-ui` ומחליף את שתיהן יחד — שני החלקים רצים בצעד אחיד, לעולם לא בגרסאות שונות.
4. **בדיקה.** לאחר ההחלפה השירות שואל את בדיקת התקינות העמוקה `/internal/health/deep`.
5. **הערכה.** אם הגרסה החדשה תקינה, העדכון נחשב מוצלח. אם לא, השירות מחזיר אוטומטית **את שני** החלקים לגרסה הקודמת ובודק שוב. אם גם זה אינו מצליח, המצב נרשם ככישלון כדי שתראו זאת.

## מה פירוש "חתום"

היצרן חותם על כל Release, ו-Klacks שלכם בודקת את החתימה לפני שהיא מקבלת חבילה. המפתח הציבורי וכתובת המניפסט הם ערכי יצרן קבועים בקובץ ה-`.env` שלכם:

- `UPDATE_MANIFEST_BASE_URL` — קבוע על מקור ה-Release של היצרן
- `UPDATE_SIGNATURE_PUBLIC_KEY` — חייב להתאים למפתח הפרטי שבו היצרן חותם

שני ערכים אלה **אינם מיועדים לשינוי**. מי שמחליף אותם מבטל את הבדיקה ובכך פותח בדיוק את הפרצה שהחתימה סוגרת.

המניפסט נושא, בין השאר: ערוץ (`Stable` או `Beta`), את הגרסה החדשה ביותר, את הגרסה המינימלית שממנה אפשר לעדכן ישירות (`MinUpgradableFrom`), את תאריך הפרסום, אם כלולה מיגרציה של מסד הנתונים, את הארטיפקטים, את החתימה וקישור לרשימת השינויים.

`klacks-api` ו-`klacks-ui` **מקובעים בקובץ ה-`.env` לגרסה מדויקת**, כדי שלא יתרחקו זה מזה בלי שיבחינו. שירות העדכונים עצמו רץ תמיד על `latest` — הוא אינו במניפסט החתום במכוון ומחליף רק את api ו-ui.

## הגדרות בתפעול

באזור ה-Admin תחת **מערכת ← עדכונים**:

| הגדרה | השפעה |
|---|---|
| **הפעלת עדכונים אוטומטיים** | עדכונים מזוהים ומוחלים אוטומטית |
| **התראה בלבד** | עדכונים רק **מזוהים**, אך אינם מוחלים עד שתפעילו אותם |
| **חלון תחזוקה** | טווח הזמן שבו מותר לעדכונים אוטומטיים לרוץ |

הגדרות אלה נשמרות במסד הנתונים וגוברות על ערכי ההתחלה מקובץ ה-`.env` ‏(`UPDATE_AUTO_ENABLED`, ‏`UPDATE_NOTIFY_ONLY`), שחלים רק בהפעלה הראשונה.

## חזרה לאחור ידנית

אוטומטית אין צורך שמישהו יתערב — עדכון שנכשל השירות מחזיר לאחור בעצמו. אם אתם רוצים במכוון צעד אחד אחורה:

1. קבעו בקובץ ה-`.env` את `KLACKS_API_TAG` ו-`KLACKS_UI_TAG` לגרסה הקודמת.
2. הפעילו מחדש את הסטאק: `docker compose up -d klacks-api klacks-ui`.
3. **אם הגרסה הפגומה כבר ביצעה מיגרציה**, שחזרו בנוסף את הגיבוי המתאים מלפני העדכון — ושימו לב למכשול בעמוד [גיבוי ושחזור](../backup-und-wiederherstellung/): טבלאות שהגרסה החדשה יצרה שורדות את השחזור וחוסמות את ההפעלה הבאה.

## טוב לדעת

- **הדרך חזרה אינה פתרון חירום אלא המקרה הרגיל.** לכל פעולת עדכון יש סטטוס: הצליחה, הוחזרה לאחור או שהדרך חזרה נכשלה. עדכון שהוחזר לאחור הוא תהליך רגיל ומתועד — לא אירוע חריג.
- **עדכון שהוחזר לאחור אינו עדכון שאופס.** החזרה לאחור משחזרת את הגרסה, לא את הנתונים שלכם. שינויי נתונים שביצעתם בין העדכון לחזרה לאחור מגיעים ממצב הגיבוי.
- **אפשר לעיין בלוגים:** ‏`docker compose logs klacks-updater` מראה את הזיהוי, הגיבוי, ההחלפה והחזרה לאחור.
