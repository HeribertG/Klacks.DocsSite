# פתרון תקלות

כאשר Klacks אינה עושה את מה שהיא אמורה לעשות, הדרך עוברת כמעט תמיד דרך הלוגים של שני השירותים החשודים — ודרך השאלה אם התהליך באמת עדיין רץ.

## קודם כול: לראות מה רץ

```bash
docker compose ps
docker compose logs klacks-api
docker compose logs klacks-updater
```

`docker compose ps` מראה אילו שירותים רצים והאם הם תקינים. `klacks-api` כותב את ההפעלה, המיגרציה ומילוי מסד הנתונים; `klacks-updater` כותב את זיהוי העדכון, הגיבוי, המעבר והחזרה לאחור.

## לוג ישן אינו הוכחה

מלכודת שכבר עלתה בזמן: קובץ הלוג עשוי לנבוע מהפעלה **קודמת**. מי שמוצא בו שגיאה וסבור שהיא הנוכחית, מחפש במקום הלא נכון.

לכן בדקו אם הלוג **עדיין גדל**:

```bash
wc -c klacks-api.log; sleep 10; wc -c klacks-api.log
```

אם הגודל נשאר זהה (תוספת של 0 בתים), התהליך כבר אינו כותב — הוא אינו רץ, ללא קשר למה שכתוב בלוג. רק שחזור חדש של התקלה עם לוג שמוכח שהוא עוקב אחרי התהליך הוא בסיס אמין.

## הודעות נפוצות ומשמעותן

| הודעה | משמעות | מה לעשות |
|---|---|---|
| `no matching manifest for linux/amd64` | אין תמונה (image) לארכיטקטורה שלכם | היצרן צריך לפרסם את התמונה למספר ארכיטקטורות (amd64 **וגם** arm64) |
| `pull access denied` | החבילה במאגר החבילות פרטית | חזרו על ההתקנה עם פרטי גישה: ‏`-GhcrUser`/‏`-GhcrToken` ב-Windows, ‏`GHCR_USER`/‏`GHCR_TOKEN` ב-Linux |
| ‏`errorCode: SETUP_REQUIRED`, ‏HTTP ‏`403` | שער ההגדרה של ה-Admin פעיל | התחברו עם `admin@test.com` וצרו את חשבון ה-Admin שלכם — ראו [התקנה ו-Playground](../../erste-schritte/installation-und-playground/) |
| הקונטיינר מסתיים ללא Managed Stacktrace עם קוד יציאה `-1` ‏(`0xffffffff`) | קריסה **נייטיבית** בספריית C/C++ שאף `try/catch` ב-C# אינו יכול לתפוס | הסתכלו בפלט הקונטיינר ב-**stderr** — שם נמצא הגורם האמיתי, לא בלוג האפליקציה |
| הקונטיינר נסגר אף שאין שגיאת אפליקציה בלוג | הליבה (Kernel) סיימה את התהליך עקב מחסור בזיכרון (OOM) | בדקו את מגבלות הזיכרון — ראו [דרישות מערכת וארכיטקטורה](../systemvoraussetzungen/) |
| ‏`42P07: relation "…" already exists` לאחר עדכון שנכשל | מיגרציה יצרה טבלאות שהשחזור לא הסיר | ראו את המכשול ב[גיבוי ושחזור](../backup-und-wiederherstellung/) |
| ה-API מתה שניות אחרי `Application started` | ההפעלה מצליחה, הקריסה מגיעה אחריה — אופייני לספרייה נייטיבית | אותו מסלול כמו בקוד היציאה `-1`: בדקו את stderr, לא את לוג האפליקציה |

במחשב **Windows-on-ARM** ‏(Snapdragon X) החיפוש הפועל מקומית נכשל בעבר בדיוק בגלל ספרייה נייטיבית כזו: ה-API דיווחה `Application started`, אך שניות לאחר מכן לא הייתה נגישה עוד עבור הממשק. אם אתם רואים את הדפוס הזה על מארח Windows מסוג ARM, ההסתכלות הראשונה היא על פלט הקונסולה (לא על לוג הקובץ) — שם הופיעה ההודעה של זיהוי המעבד הנוגע בדבר.

## איך מצמצמים תקלה

1. **מה בדיוק עשיתם**, ומה ציפיתם? הצעד האחרון לפני התקלה הוא חצי מהתשובה.
2. **אילו שירותים רצים?** ‏`docker compose ps`.
3. **האם הלוג עדיין גדל?** ראו למעלה.
4. **מה הופיע לאחרונה ב-stderr?** בקריסות נייטיביות זה המקור היחיד.
5. **מה השתנה לאחרונה?** עדכון, הגדרה, תעודה חדשה.

## טוב לדעת

- **שירות שהופעל מוקדם ושירות תקין נראים זהים בלוג.** אם דבר אינו מגיע לממשק, בדקו אם התהליך בכלל עדיין רץ — ולא רק מה שהוא כתב לאחרונה.
- **בקריסה ללא שגיאת אפליקציה, הזיכרון הוא החשוד הראשון**, במיוחד לאחר עדכון עם מודלי חיפוש חדשים.
- **פרטים מועילים לדיווח:** הגרסה הנוגעת בדבר (`KLACKS_API_TAG`/‏`KLACKS_UI_TAG` מקובץ ה-`.env`), הפלט של `docker compose ps`, השורות האחרונות של שני הלוגים והצעד האחרון לפני התקלה. נא **ללא** סיסמאות ומפתחות מקובץ ה-`.env`.
