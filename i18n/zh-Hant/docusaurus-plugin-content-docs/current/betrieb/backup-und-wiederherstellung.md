# 備份與還原

您的資料完全存放在自己的基礎設施上 — 因此備份也由您負責。本頁說明哪些內容必須備份，以及如何還原。

## 必須備份的內容

| 內容 | 位置 | 頻率 |
|---|---|---|
| 資料庫 | 磁碟區 `postgres_data` | 每天，至少在每次更新前 |
| 上傳檔案 | 磁碟區 `api-uploads` | 與資料庫一併備份 |
| 文件 | 磁碟區 `api-documents` | 與資料庫一併備份 |
| 金鑰環 | 磁碟區 `api-dataprotection` | 與資料庫一併備份，**務必** |

磁碟區 `api-dataprotection` 內含金鑰環，Klacks 用它來解密加密後的設定（例如通訊管道的存取憑證）。沒有這個金鑰環的資料庫雖然存在，卻無法完整使用 — 請務必一併備份。

## 備份資料庫

```bash
docker exec klacks-postgres pg_dump -U admin -d Klacks -Fc > klacks-20260922.dump
```

格式 `-Fc`（custom）會壓縮資料，並允許在還原時只挑選個別資料表。

## 還原資料庫

```bash
docker exec -i klacks-postgres pg_restore -U admin -d Klacks --clean --if-exists < klacks-20260922.dump
```

`--clean --if-exists` 會先清除既有物件，避免還原時因資料表已存在而失敗。

## 常見陷阱：遷移失敗後的回復

過去正是在這裡造成了一次正式環境的停機，其機制與任何以傾印檔為基礎的回復都相同：

如果有問題的版本透過遷移建立了**新資料表**，這些資料表並不在傾印檔中。因此還原之後，資料庫不會停留在舊的狀態 — 新資料表會在還原後**繼續存在**，而遷移歷史記錄（`__EFMigrationsHistory`）卻被重設回舊的狀態。下一次啟動嘗試就會遇到錯誤 `42P07: relation "…" already exists`，安裝因而陷入重啟迴圈。

因此，如果您在更新失敗後手動回復，請在還原之後檢查是否殘留了舊版本中尚不存在的資料表，並在重新啟動 API **之前**將它們移除。

## 保留與刪除

Klacks 刪除資料時不只是標記刪除，而是**實體**刪除。一個背景服務每天執行，不可逆地移除所有標記為已刪除、且刪除時間已超過所設定期限的資料列 — 而且涵蓋**所有**帶有刪除標記的資料表（員工、地址、群組、班次、工時、缺勤、休息時間等等）。沒有例外清單；刪除義務刻意優先於可還原性。

期限透過設定 `DATA_RETENTION_DAYS` 控制；若未自行指定，預設值為 **3650 天（10 年）**。[資料保留](../../einstellungen/system-sicherheit/datenaufbewahrung/)頁面詳細說明了這項設定。

## 小提醒

- **Klacks 會在每次更新前自行備份。** 更新服務會在啟用新版本之前建立資料備份；若包含遷移，該備份會繫結在更新作業上，並重複用於自動或手動回復。這並不能取代您自己的**外部**備份 — 外部備份可防範主機本身受損的情況。
- **請驗證您的備份。** 從未還原過的傾印檔只是一種假設，而不是備份。請先建立一個用完即丟的資料庫並還原到其中，再決定是否信賴這套流程。
- **請將金鑰環與資料庫分開保存。** 如果 `api-dataprotection` 與資料庫位於同一組備份中，而同一個事件又同時波及兩者，加密就形同虛設。
