# 更新與回復

Klacks 會自行更新 — 使用已簽署的套件、每個步驟前先備份，並在出問題時自動回復。本頁說明其間發生的事，以及您可以如何介入。

## 更新如何進行

1. **偵測。** API 會查詢開發商隨每次發行而發布的已簽署資訊清單。如果其中記載了較新的版本，更新即視為可用。
2. **備份。** 更新服務會建立資料庫的資料備份。若新版本包含遷移，該備份會被固定繫結在這次更新作業上，之後可供回復使用。
3. **下載並一併啟用。** 服務會下載 `klacks-api` **與** `klacks-ui` 的新映像檔，並將兩者一併切換 — 兩個部分同步運行，絕不會處於不同版本。
4. **檢查。** 切換之後，服務會查詢深度健康檢查 `/internal/health/deep`。
5. **評估。** 如果新版本健康，更新即視為成功。如果不健康，服務會自動將**兩個**部分回復至先前的版本並再次檢查。若這一步也失敗，狀態會記錄為失敗，讓您看得到。

## 「已簽署」是什麼意思

開發商會為每次發行簽署，而您的 Klacks 在接受任何套件之前都會驗證簽章。公開金鑰與資訊清單的位址，是您 `.env` 中固定的開發商數值：

- `UPDATE_MANIFEST_BASE_URL` — 固定指向開發商的發行來源
- `UPDATE_SIGNATURE_PUBLIC_KEY` — 必須與開發商用來簽署的私密金鑰相符

這兩個數值**不應被更改**。更換它們會取消驗證，也就等於打開了簽章原本要封閉的漏洞。

資訊清單包含：通道（`Stable` 或 `Beta`）、最新版本、可直接更新的最低版本（`MinUpgradableFrom`）、發行日期、是否包含資料庫遷移、套件內容、簽章，以及指向變更清單的連結。

`klacks-api` 與 `klacks-ui` 在 `.env` 中**固定為確切的版本**，以免它們在不知不覺中分歧。更新服務本身一律使用 `latest` — 它刻意不列在已簽署的資訊清單中，並且只會更換 api 與 ui。

## 營運中的設定

在管理員區域的 **系統 → 更新**：

| 設定 | 作用 |
|---|---|
| **啟用自動更新** | 更新會被偵測並自動套用 |
| **僅通知** | 更新只會被**偵測**，在您手動觸發之前不會套用 |
| **維護時段** | 允許自動更新執行的時間範圍 |

這些設定存放在資料庫中，並優先於 `.env` 的啟動值（`UPDATE_AUTO_ENABLED`、`UPDATE_NOTIFY_ONLY`）— 後者只在首次啟動時生效。

## 手動回復

自動情況下，沒有人需要介入 — 失敗的更新會由服務自行回復。如果您刻意想退回一步：

1. 在 `.env` 中，將 `KLACKS_API_TAG` 與 `KLACKS_UI_TAG` 設為先前的版本。
2. 重新啟用堆疊：`docker compose up -d klacks-api klacks-ui`。
3. **如果有問題的版本已經執行過遷移**，請另外還原更新前對應的備份 — 並請注意[備份與還原](../backup-und-wiederherstellung/)頁面中的常見陷阱：新版本建立的資料表在還原後仍會保留，並會阻擋下一次啟動。

## 小提醒

- **回復不是權宜之計，而是常態。** 每個更新作業都有一個狀態：成功、已回復，或回復失敗。已回復的更新是一個正常且有記錄的流程 — 並非事故。
- **已回復的更新不等於已重設的更新。** 回復還原的是版本，而不是您的資料。您在更新與回復之間所做的資料變更，會來自備份當時的狀態。
- **您可以在日誌中查看：** `docker compose logs klacks-updater` 會顯示偵測、備份、切換與回復。
