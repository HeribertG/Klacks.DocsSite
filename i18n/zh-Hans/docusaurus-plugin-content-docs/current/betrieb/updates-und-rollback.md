# 更新与回滚

Klacks 会自行更新 — 使用签名的软件包，每一步之前都先备份，出现问题时自动回退。本页说明其间会发生什么，以及您如何介入。

## 更新如何进行

1. **检测。** API 查询厂商随每个版本发布的签名清单。如果其中记录了更新的版本，就认为有可用更新。
2. **备份。** 更新服务为数据库创建一份数据备份。如果新版本包含迁移，该备份会被牢固地绑定到这次更新操作，并留待之后用于回退。
3. **拉取并一起激活。** 服务拉取 `klacks-api` **和** `klacks-ui` 的新镜像，并将两者同时切换 — 这两部分步调一致，绝不会运行在不同版本上。
4. **检查。** 切换之后，服务会调用深度健康检查 `/internal/health/deep`。
5. **评估。** 如果新版本健康，更新即视为成功。如果不健康，服务会自动将**两个**部分都回滚到上一个版本，并再次检查。如果这也不成功，则会将状态记录为失败，以便您看到。

## 「签名」意味着什么

厂商会为每个版本签名，您的 Klacks 在接受软件包之前会验证签名。公钥和清单地址是 `.env` 中由厂商固定的值：

- `UPDATE_MANIFEST_BASE_URL` — 固定指向厂商的发布来源
- `UPDATE_SIGNATURE_PUBLIC_KEY` — 必须与厂商用于签名的私钥相匹配

这两个值**不应被更改**。一旦替换，就等于取消了验证，恰好打开了签名本来要堵住的漏洞。

清单中包含：渠道（`Stable` 或 `Beta`）、最新版本、可直接更新的最低版本（`MinUpgradableFrom`）、发布日期、是否包含数据库迁移、制品、签名，以及指向变更列表的链接。

`klacks-api` 和 `klacks-ui` 在 `.env` 中**固定到确切的版本**，以免它们在不知不觉中产生偏差。更新服务本身始终运行 `latest` — 它有意不在签名清单之内，且只替换 api 和 ui。

## 运营中的设置

在管理员区域的 **系统 → 更新** 中：

| 设置 | 作用 |
|---|---|
| **启用自动更新** | 检测更新并自动应用 |
| **仅通知** | 只**检测**更新，在您手动触发之前不会应用 |
| **维护窗口** | 允许自动更新运行的时间段 |

这些设置保存在数据库中，并优先于 `.env` 中的初始值（`UPDATE_AUTO_ENABLED`、`UPDATE_NOTIFY_ONLY`），后者只在首次启动时生效。

## 手动回滚

自动情况下无需任何人介入 — 失败的更新由服务自行回滚。如果您有意想退回一步：

1. 在 `.env` 中把 `KLACKS_API_TAG` 和 `KLACKS_UI_TAG` 设置为上一个版本。
2. 重新激活服务栈：`docker compose up -d klacks-api klacks-ui`。
3. **如果有缺陷的版本已经执行过迁移**，请另外恢复更新之前对应的备份 — 并请注意[备份与恢复](../backup-und-wiederherstellung/)一页中的陷阱：新版本创建的表在恢复后依然存在，并会阻碍下一次启动。

## 小贴士

- **回退不是应急方案，而是常规流程。** 每一次更新操作都有状态：成功、已回滚，或回退失败。已回滚的更新是一次正常的、有记录的操作 — 并非事故。
- **已回滚的更新并不等于被重置的更新。** 回滚恢复的是版本，而不是您的数据。您在更新与回退之间所做的数据改动，来自备份时的状态。
- **您可以在日志中查看：** `docker compose logs klacks-updater` 会显示检测、备份、切换和回退。
