# 备份与恢复

您的数据完全保存在您自己的基础设施上 — 因此备份也由您负责。本页说明需要备份什么，以及如何把它恢复回来。

## 需要备份什么

| 对象 | 位置 | 频率 |
|---|---|---|
| 数据库 | 数据卷 `postgres_data` | 每天，至少在每次更新之前 |
| 上传文件 | 数据卷 `api-uploads` | 与数据库一同备份 |
| 文档 | 数据卷 `api-documents` | 与数据库一同备份 |
| 密钥环 | 数据卷 `api-dataprotection` | 与数据库一同备份，**务必** |

数据卷 `api-dataprotection` 中保存着密钥环，Klacks 用它来解密加密的设置（例如通信渠道的访问凭据）。没有这个密钥环，数据库虽然在，却无法完整使用 — 请务必始终一并备份。

## 备份数据库

```bash
docker exec klacks-postgres pg_dump -U admin -d Klacks -Fc > klacks-20260922.dump
```

`-Fc`（custom）格式会进行压缩，恢复时还可以选择单个表。

## 恢复数据库

```bash
docker exec -i klacks-postgres pg_restore -U admin -d Klacks --clean --if-exists < klacks-20260922.dump
```

`--clean --if-exists` 会先清除已有的对象，避免恢复因表已存在而失败。

## 陷阱：迁移失败后的回滚

过去的一次生产故障正是出在这里，其机制适用于所有基于转储的回滚：

如果某个有缺陷的版本通过迁移创建了**新表**，这些表并不在转储中。因此恢复之后，数据库并不会回到旧状态 — 新表在恢复后**依然存在**，而迁移历史（`__EFMigrationsHistory`）却被重置为旧状态。下一次启动就会遇到错误 `42P07: relation "…" already exists`，安装陷入重启循环。

如果您在更新失败后手动回滚，请在恢复完成后检查是否残留了旧版本中还不存在的表，并在重新启动 API **之前**将其删除。

## 保留与删除

Klacks 删除数据不只是打上删除标记，而是**物理**删除。一个后台服务每天运行，不可恢复地清除所有已标记为删除、且删除时间早于所配置期限的行 — 范围涵盖**所有**带删除标记的表（员工、地址、分组、班次、工时、缺勤、休息等等）。没有例外名单；删除义务有意优先于可恢复性。

期限通过设置 `DATA_RETENTION_DAYS` 控制；若不自行指定，默认值为 **3650 天（10 年）**。[数据保留](../../einstellungen/system-sicherheit/datenaufbewahrung/)一页详细介绍了该设置。

## 小贴士

- **每次更新之前，Klacks 会自行备份。** 更新服务在激活新版本之前会创建一份数据备份；如果包含迁移，该备份会绑定到这次更新操作，并在自动或手动回滚时重复使用。这并不能取代您自己的**外部**备份 — 外部备份正是为了应对主机本身出问题的情形。
- **请验证您的备份。** 从未恢复过的转储只是一种假设，不是备份。请先创建一个可丢弃的数据库并恢复到其中，再决定是否信赖这套流程。
- **请把密钥环与数据库分开保管。** 如果 `api-dataprotection` 与数据库在同一个备份集中，而同一次事故同时波及两者，加密就形同虚设。
