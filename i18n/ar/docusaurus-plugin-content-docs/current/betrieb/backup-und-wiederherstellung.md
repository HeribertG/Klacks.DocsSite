# النسخ الاحتياطي والاستعادة

بياناتكم موجودة بالكامل على بنيتكم التحتية الخاصة — ولذلك فإن النسخ الاحتياطي من مسؤوليتكم أيضًا. توضح هذه الصفحة ما يجب نسخه احتياطيًا وكيفية استعادته.

## ما يجب نسخه احتياطيًا

| ماذا | أين | كم مرة |
|---|---|---|
| قاعدة البيانات | الـ volume ‏`postgres_data` | يوميًا، وعلى الأقل قبل كل تحديث |
| الملفات المرفوعة | الـ volume ‏`api-uploads` | مع قاعدة البيانات |
| المستندات | الـ volume ‏`api-documents` | مع قاعدة البيانات |
| سلسلة المفاتيح | الـ volume ‏`api-dataprotection` | مع قاعدة البيانات، **بلا استثناء** |

يحتوي الـ volume ‏`api-dataprotection` على سلسلة المفاتيح التي يفك بها Klacks تشفير الإعدادات المشفّرة (مثل بيانات الوصول إلى قنوات التواصل). قاعدة البيانات دون سلسلة المفاتيح هذه موجودة، لكنها غير قابلة للاستخدام بالكامل — لذا انسخوها احتياطيًا دائمًا.

## نسخ قاعدة البيانات احتياطيًا

```bash
docker exec klacks-postgres pg_dump -U admin -d Klacks -Fc > klacks-20260922.dump
```

الصيغة `-Fc` (custom) تضغط البيانات وتتيح عند الاستعادة اختيار جداول بعينها.

## استعادة قاعدة البيانات

```bash
docker exec -i klacks-postgres pg_restore -U admin -d Klacks --clean --if-exists < klacks-20260922.dump
```

يزيل الخيار `--clean --if-exists` الكائنات الموجودة مسبقًا، حتى لا تفشل الاستعادة بسبب جداول موجودة أصلًا.

## العقبة: التراجع بعد ترحيل (Migration) فاشل

هنا بالذات وقع انقطاع في بيئة الإنتاج سابقًا، وآليته هي آلية أي تراجع قائم على ملف تفريغ (Dump):

إذا أنشأ إصدار معيب **جداول جديدة** عبر ترحيل، فإن هذه الجداول ليست في ملف التفريغ. وبالتالي لا تبقى قاعدة البيانات عند الحالة القديمة بعد الاستعادة — إذ **تبقى** الجداول الجديدة بعد الاستعادة، بينما يُعاد ضبط سجل الترحيلات (`__EFMigrationsHistory`) إلى الحالة القديمة. وعند محاولة البدء التالية يظهر الخطأ `42P07: relation "…" already exists` ويعلق التثبيت في حلقة إعادة تشغيل.

لذلك، إذا تراجعتم يدويًا بعد تحديث فاشل، فتحققوا بعد الاستعادة مما إذا كانت قد بقيت جداول لم تكن موجودة في الإصدار القديم، وأزيلوها **قبل** أن تشغّلوا الـ API من جديد.

## الاحتفاظ والحذف

لا يحذف Klacks البيانات بعلامة حذف فحسب، بل **فعليًا**. تعمل خدمة خلفية يوميًا وتزيل نهائيًا كل الصفوف الموسومة كمحذوفة التي مضى على وقت حذفها أكثر من المهلة المضبوطة — وذلك عبر **جميع** الجداول التي تحمل علامة الحذف (الموظفون، العناوين، المجموعات، الدوامات، أوقات العمل، الغيابات، الاستراحات وغيرها). لا توجد قائمة استثناءات؛ فواجب الحذف مقدَّم عمدًا على إمكانية الاستعادة.

تتحكمون في المهلة عبر الإعداد `DATA_RETENTION_DAYS`؛ وفي حال عدم تحديد قيمة تسري القيمة الافتراضية **3650 يومًا (10 سنوات)**. تصف صفحة [الاحتفاظ بالبيانات](../../einstellungen/system-sicherheit/datenaufbewahrung/) هذا الإعداد بالتفصيل.

## من المفيد معرفته

- **Klacks ينسخ احتياطيًا بنفسه قبل كل تحديث.** تنشئ خدمة التحديث نسخة احتياطية قبل تفعيل إصدار جديد؛ وفي حالة وجود ترحيل ترتبط النسخة بعملية التحديث وتُستخدم مجددًا عند التراجع التلقائي أو اليدوي. وهذا لا يغني عن نسخة احتياطية **خارجية** خاصة بكم — فهي تحميكم تحديدًا في الحالات التي يتضرر فيها المضيف نفسه.
- **تحققوا من نسختكم الاحتياطية.** ملف التفريغ الذي لم يُستعَد قط افتراض، وليس نسخة احتياطية. أنشئوا قاعدة بيانات للتجربة واستعيدوا إليها قبل أن تعتمدوا على هذا الإجراء.
- **احفظوا سلسلة المفاتيح منفصلة عن قاعدة البيانات.** إذا كان `api-dataprotection` ضمن مجموعة النسخ الاحتياطي نفسها وأصابت الحادثة نفسها الاثنين معًا، فلا قيمة للتشفير.
