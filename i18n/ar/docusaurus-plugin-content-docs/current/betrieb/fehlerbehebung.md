# استكشاف الأخطاء وإصلاحها

عندما لا يفعل Klacks ما يُفترض به، فإن الطريق يمر دائمًا تقريبًا عبر سجلات الخدمتين المشتبه بهما — وعبر سؤال: هل ما زالت العملية تعمل فعلًا؟

## أولًا: معرفة ما يعمل

```bash
docker compose ps
docker compose logs klacks-api
docker compose logs klacks-updater
```

يعرض `docker compose ps` الخدمات التي تعمل وهل هي سليمة. يسجّل `klacks-api` البدء والترحيل وتعبئة قاعدة البيانات؛ ويسجّل `klacks-updater` اكتشاف التحديث والنسخ الاحتياطي والتبديل والتراجع.

## السجل القديم ليس دليلًا

فخ كلّف وقتًا سابقًا: قد يعود ملف السجل إلى تشغيل **سابق**. ومن يجد فيه خطأً ويظنه الخطأ الحالي يبحث في المكان الخطأ.

لذلك تحققوا مما إذا كان السجل **ما زال ينمو**:

```bash
wc -c klacks-api.log; sleep 10; wc -c klacks-api.log
```

إذا بقي الحجم كما هو (زيادة 0 بايت)، فإن العملية لم تعد تكتب — أي أنها لا تعمل، بغض النظر عمّا يحتويه السجل. فقط تكرار جديد للخطأ مع سجل يُثبت أنه يواكب العملية يُعدّ أساسًا موثوقًا.

## الرسائل الشائعة ومعناها

| الرسالة | المعنى | ما العمل |
|---|---|---|
| `no matching manifest for linux/amd64` | لا توجد الصورة (image) لمعماريتكم | يجب على الشركة المصنّعة نشر الصورة متعددة المعماريات (amd64 **و** arm64) |
| `pull access denied` | الحزمة في سجل الحزم خاصة | أعيدوا التثبيت مع بيانات الدخول: ‏`-GhcrUser`/‏`-GhcrToken` على Windows، و`GHCR_USER`/‏`GHCR_TOKEN` على Linux |
| ‏`errorCode: SETUP_REQUIRED`، ‏HTTP ‏`403` | بوابة إعداد المدير مفعّلة | سجّلوا الدخول بـ `admin@test.com` وأنشئوا حساب المدير الخاص بكم — راجعوا [التثبيت وبيئة التجربة](../../erste-schritte/installation-und-playground/) |
| تنتهي الحاوية دون Managed Stacktrace برمز الخروج `-1` ‏(`0xffffffff`) | انهيار **أصلي** (Native) في مكتبة C/C++ لا يستطيع أي `try/catch` في C# التقاطه | انظروا إلى مخرجات الحاوية على **stderr** — فهناك السبب الفعلي، وليس في سجل التطبيق |
| تُنهى الحاوية رغم عدم وجود خطأ تطبيق في السجل | أنهى النواة (Kernel) العملية بسبب نقص الذاكرة (OOM) | افحصوا حدود الذاكرة — راجعوا [متطلبات النظام والبنية](../systemvoraussetzungen/) |
| ‏`42P07: relation "…" already exists` بعد تحديث فاشل | أنشأ ترحيل جداول لم تُزلها الاستعادة | راجعوا العقبة في [النسخ الاحتياطي والاستعادة](../backup-und-wiederherstellung/) |
| تتوقف الـ API بعد ثوانٍ من `Application started` | ينجح البدء ويأتي الانهيار بعده — وهذا نموذجي لمكتبة أصلية | المسار نفسه كما في رمز الخروج `-1`: افحصوا stderr، لا سجل التطبيق |

على **جهاز Windows-on-ARM** ‏(Snapdragon X) فشل البحث المحلي سابقًا بسبب مكتبة أصلية من هذا النوع تحديدًا: أبلغت الـ API ‏`Application started`، لكنها بعد ثوانٍ لم تعد قابلة للوصول من الواجهة. إذا رأيتم هذا النمط على مضيف Windows بمعمارية ARM، فانظروا أولًا إلى مخرجات وحدة التحكم (Console) — لا إلى سجل الملف — ففيها ظهرت رسالة اكتشاف المعالج المعني.

## كيف تحصرون الخطأ

1. **ماذا فعلتم بالضبط**، وماذا توقعتم؟ آخر خطوة قبل الخطأ نصف الإجابة.
2. **أي الخدمات تعمل؟** ‏`docker compose ps`.
3. **هل ما زال السجل ينمو؟** راجعوا أعلاه.
4. **ماذا ظهر أخيرًا على stderr؟** في حالات الانهيار الأصلي هو المصدر الوحيد.
5. **ما الذي تغيّر مؤخرًا؟** تحديث، أو إعداد، أو شهادة جديدة.

## من المفيد معرفته

- **الخدمة التي بدأت مبكرًا والخدمة السليمة تبدوان متماثلتين في السجل.** إذا لم يصل شيء إلى الواجهة، فتحققوا مما إذا كانت العملية ما زالت تعمل أصلًا — لا مما كتبته آخر مرة فحسب.
- **عند الانهيار دون خطأ تطبيق، فالذاكرة هي المشتبه به الأول**، خصوصًا بعد تحديث يضيف نماذج بحث جديدة.
- **بيانات مفيدة لأي بلاغ:** الإصدار المعني (`KLACKS_API_TAG`/‏`KLACKS_UI_TAG` من ملف `.env`)، ومخرجات `docker compose ps`، وآخر أسطر السجلين، وآخر خطوة قبل الخطأ. يُرجى **عدم** إرفاق كلمات المرور والمفاتيح من ملف `.env`.
